# Анализ проблем и рисков текущей архитектуры

## Текущее состояние

**Взаимодействия:**
- `core-app` запрашивает данные о продуктах у `ins-product-aggregator` каждые 15 минут через REST
- `ins-comp-settlement` запрашивает данные о продуктах у `ins-product-aggregator` раз в сутки через REST
- `ins-comp-settlement` запрашивает список оформленных страховок у `core-app` раз в сутки через REST
- При каждом запросе `ins-product-aggregator` синхронно опрашивает все 5 страховых компаний и агрегирует результат

## Выявленные проблемы

### 1. Синхронная агрегация данных от страховых компаний

Сейчас уже возникают задержки и таймауты при запросах к `ins-product-aggregator`. При росте с 5 до 10 компаний:
- Время агрегации увеличится с ~1 секунды до ~2 секунд
- Вероятность успешного ответа упадет с 95% до 90%
- Риск превысить стандартные HTTP timeout (3-5 секунд)

Недоступность одной страховой компании блокирует получение данных по всем остальным.

### 2. Polling вместо push

`core-app` делает 96 запросов в сутки к `ins-product-aggregator`, хотя тарифы могут не меняться днями. Это создает:
- Ненужную нагрузку на сервис
- Окно неактуальности данных до 15 минут
- Проблемы масштабирования при добавлении новых потребителей данных

### 3. Batch-синхронизация страховок

Передача всех оформленных страховок раз в сутки через REST:
- При росте бизнеса размер ответа может превысить разумные лимиты (несколько MB)
- Задержка обработки взаиморасчетов до 24 часов
- При сбое нужно повторно передавать весь массив данных

### 4. Жесткая связанность сервисов

Синхронные REST вызовы создают зависимости:
- `ins-product-aggregator` недоступен → `core-app` и `ins-comp-settlement` не могут обновить данные
- Изменение API требует согласованного обновления всех потребителей
- Нет механизма автоматического восстановления при сбоях

### 5. Несогласованность локальных реплик

`core-app` и `ins-comp-settlement` хранят копии данных о продуктах, но обновляют их в разное время:
- `core-app` обновляется каждые 15 минут
- `ins-comp-settlement` обновляется раз в сутки
- Клиент может видеть одни тарифы, а в реестре зафиксируются другие

### 6. Производительность под нагрузкой

Синхронные HTTP-запросы блокируют потоки:
- При увеличении нагрузки пул подключений может исчерпаться
- Нет приоритизации запросов
- Медленный ответ одной компании замедляет весь процесс
